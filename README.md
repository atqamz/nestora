# Nestora

Mobile-first PWA that tracks a household's planning in one place.
React + TypeScript SPA served by a Cloudflare Worker with D1. During the move to a new name the app answers on both `wp.atqamz.com` and `nestora.atqamz.com`.

## Run locally

CI uses the newest Node release: `.node-version` is `latest`, and `actions/setup-node` resolves it from nodejs.org on every run. mise ignores `.node-version` by default; run `mise settings add idiomatic_version_file_enable_tools node` to read it, or `mise use node@latest`. `latest` means the newest installed version, so run `mise install node@latest` to move it forward; a local machine can lag CI until you do.

```sh
npm ci
npm run dev
npm run check
```

`npm run dev` serves the SPA and `/api/health` with a local D1. `npm run preview` serves the production build. The local D1 state lives in `.wrangler`. `npm run dev` does not apply the migration: on a fresh `.wrangler`, run `npx wrangler d1 migrations apply wp --local --env dev` once, otherwise `/api/sync` returns 500. After a change to `migrations/0001_init.sql` (it is the initial schema and is edited in place) delete `.wrangler` and apply the migration again.

## Sync and privacy limits

- A private routine and its actions never reach the other partner. The global `rev` is the one thing that does: a private write moves the `rev` that the other partner's pull, push response and JSON export report, with no row behind it. The other partner can tell that some write happened and when, never what or in which routine. Accepted because it is a bare counter between two household members. Rejected: a `rev` per side. It changes the cursor meaning of all sync, needs a cursor reset on every client, and a client with an old cursor can lose rows. `test/routines-private.test.ts` pins this.
- A create on the id of a hidden row answers `404 row_id: no such row`, while a create on an absent id succeeds. Telling the two apart needs the other partner's random UUID. Pinned in the same file. Revisit it if a routine id is ever stored where the other partner can read it, such as an order list or a link.
- The routine day is fixed to UTC+7 with a 04:00 cut-off (`shared/routines.ts`) and ignores `settings.timezone`. The default zone is Asia/Jakarta, which has no daylight saving time. `test/routines-schedule.test.ts` pins the cut-off.
- Start mode timers run on the phone only. The end instant is kept in `sessionStorage` for the tab as `wp.timer.<side>.<routine>.<action>`, so a reload or a locked screen shows the right time left. The key holds the routine id, so it is the one routine id in a store the other partner's tab could read: every `wp.timer.` key of the other side, every key without a side and every key stale for over an hour is deleted when a probe confirms a side (`createSession` calls `timers.purge`), and a stale one is deleted when read. A timer belongs to its action: moving to another step, Back, Skip, Exit and the 04:00 day change delete it, and a reload opens on the step that holds a running timer. Leaving Start by another route keeps the timer for up to an hour so the step can resume. If the other partner signs in on the same tab between two visits, the first partner's timers are gone when they come back. Nothing rings while the app is closed or in the background until reminders ship. The tone needs a tap on the page after a reload (browser autoplay rules), and the screen wake lock needs Safari 16.4 or later, or iOS 18.4 in the Home Screen app: where it is missing the screen shows one hint line.
- A timetable is a routine in the `timetable` moment whose actions are `block`s, owned by one partner and shared unless it was made private. A block belongs to the weekday it is listed under (its own `days`, else the routine's) and its times are plain clock times of that day: an end must be after the start, a block cannot cross midnight, and no end means "until the end of the day". A block before 04:00 sorts first on its weekday and counts as finished as soon as that routine day starts, because the day changes at 04:00 and "Partner today" reads the routine day. The "Partner today" block on Home (named after the partner's nickname when one is set, for example "Sam today") lists the other partner's visible timetable for the routine day, read only, refreshed once a minute with the same hook as the Today block; a private timetable never reaches it, since the rows are filtered before they arrive. A paused timetable lists nothing. Only the current week is shown. `test/timetable.test.ts` and `test/timetable-ui.test.ts` pin this.
- The browser keeps one database per side, `wp-a` and `wp-b`, and nothing is cleared when the signed-in side changes: the app opens only the partition of the side the server reports, so the other side's rows, unsent changes and rejections are not in the database it has open. A start sends a probe with no side (`GET /api/sync?since=9007199254740991`, which returns no rows), opens the partition of the `me` in the answer, and shows and sends nothing before that. Every `/api/sync` and `/api/export` request carries the side it was made for (`X-Wp-Side`; an export link carries `side=` in its query because a link cannot set a header). When it differs from the signed-in side the Worker answers `409 side_mismatch` and does no read and no write. A tab that gets it stops syncing, keeps its partition untouched, parks nothing as rejected and shows "Signed in as someone else. Reload this page.", so a tab loaded as one partner cannot write under the other. A request without the header is served as before. The one trade-off: when the probe fails (no network, a probe that gets no answer within 4 s, an expired login) the app opens the partition of the last confirmed side, a hint in `localStorage`, read-only, without waiting longer. That is the device's own last state, but another partner who signs in on the same device sees it until the first answer, which switches to their own partition. While the side is unconfirmed every write (create, update, remove, import, settings, discarding a parked entry) is refused with "Sign-in not confirmed yet. Changes are paused. Try again when you are back online." and nothing is queued or written, so no entry can end up in the other partner's partition. The probe is retried after 5 s, 15 s, 60 s and then every 60 s, and on `online` and `visibilitychange`; the answer lifts the pause on the same side or opens the other side's partition, with no reload. An expired login with a hint keeps the read-only state and offers "Log in again". A tab in `mismatch` renders no rows. With no hint and no network nothing opens. The database that predates the partitions (`wp`) is copied once into the first side the server confirms, if that side or nobody used it last, and is kept as it was apart from a marker. `test/partition.test.ts` and `test/worker-side.test.ts` pin this.

## Calendar feed

- `GET /feed/<token>.ics` serves a partner's own timetable and the routines that have a calendar time (`start_time`, optional `duration`, 15 minutes when absent) and are theirs or shared. Private routines, the other partner's routines and the other partner's timetable are never in it. Google's servers fetch the feed, so it sits outside Cloudflare Access: the Access application covers only `/api/*` and `/design/*`, and `run_worker_first` lists `/feed/*` so the Worker answers before the static assets.
- The token is 32 random bytes as 64 lowercase hex characters, shown once when it is made in Settings. Only its SHA-256 is stored, in the server-only `feed_tokens` table (`migrations/0002_feed.sql`, one row per partner, never synced, exported or returned). A new token replaces the old one at once. Every request, malformed or unknown or valid, hashes the path, reads both rows and compares each in constant time, so a wrong token costs the same as a right one and always answers the same 404.
- There is no rate limit: the free plan has no rate limit rule that code can set, and 256 random bits cannot be guessed. A flood of requests spends the Worker's daily request quota, which `/api/*` shares; an operator who sees that can revoke the token and add a Cloudflare WAF rule on `/feed/*`.
- The token is part of the URL, so Cloudflare's own request logs and analytics can show it, and anyone holding the link can read the feed until it is revoked. Responses carry `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`, and the Worker logs no URL.
- The horizon is the last 7 and the next 90 routine days. A series starts at its first occurrence inside it and ends with `UNTIL` at its last. A pause is always a prefix of a series, so it moves the start; holidays and other gaps become `EXDATE`. Calendar apps refresh subscribed feeds on their own schedule, usually hours.

## Books lookup

- `GET /api/lookup` sits under `/api/*`, so Cloudflare Access protects it, and answers only a signed-in caller. Parameters: `isbn` (13 digits with a valid check digit) or `title` (2 to 200 characters) with an optional `author` (up to 120). Anything else is `400 {"error":"bad_query"}`. The answer is `{"hits":[...]}`, at most 8 candidates in the order the source gave them: `source` (`google` or `openlibrary`), `work` (Google volume id or Open Library work key), `title`, `author`, `year`, `cover`, `isbns` (ISBN-13 only), `language`, `blurb` (always `null` for a Google hit). Failures are `{"error":"busy","retry":<seconds>}` with `Retry-After` (status 429 or 503, when Google or Open Library is limited or down) or `{"error":"failed"}` (502). An error body never holds the upstream URL. The route is read-only and carries no per-partner data, so it is not in the side check (`SIDED` in `worker/index.ts`) that guards `/api/sync`, `/api/export` and `/api/feed`; like `/api/me` it answers whichever partner is signed in, whatever `X-Wp-Side` says.
- Google Books is asked first with a plain query (`<title> <author>`, or `isbn:<13>`). The `intitle:` and `inauthor:` operators return nothing for these titles, so they are never sent. Open Library is asked next, from the Worker, when Google returns nothing usable, answers with an error, answers `totalItems` above zero with no usable volume (an upstream oddity, never taken for a miss) or the key is absent. The first source with answers wins and the lists are never mixed: Google's terms forbid reordering or altering its results, and its branding rules forbid showing them with third-party results. The browser asks Open Library directly only when the Worker cannot be reached (a network error, a login redirect or a non-JSON answer). Offline still shows "Offline: type it in."
- The secret is `GOOGLE_BOOKS_KEY`, a Cloudflare Worker secret for a key restricted to the Books API: `wrangler secret put GOOGLE_BOOKS_KEY`. It is optional: without it, or with a blank value, the route uses Open Library only. Locally, put it in `.dev.vars` (`.dev.vars.example` has the empty line); the file is git-ignored. It is read only in `worker/lookup.ts` and sent only to Google, in the `x-goog-api-key` request header, so it is in no URL, response, log line or cache entry. The Worker sends Open Library the `User-Agent` `Nestora/1.0 (+https://nestora.atqamz.com)`, which Open Library asks for.
- Why the data is handled as it is: the Google APIs Terms of Service (section 5e) forbid building permanent copies of what the API returns and keeping cached copies longer than the cache headers allow. So nothing from Google lives long, and nothing that is only Google's text is kept at all.
- Cache: the Workers Cache API (`caches.default`) under a synthetic key built from the folded query (`https://lookup.invalid/v1?title=...&author=...`, no key in it). Every answer, found or empty, from Google or from Open Library, is kept for at most 1 hour (`max-age=3600`), and only when Google answered; an error, an oddity, or an answer given while Google failed or was not asked, is never kept. Each entry also carries its own timestamp, and an entry older than an hour, or stamped in the future, is not served even if the cache still holds it. The client sees `Cache-Control: no-store`. A cache that fails is skipped, never an error. The Cache API is per data center, so a repeat from another region asks Google again.
- What a book row keeps from Google: facts (title, author, ISBN, language, year), the volume id (`data.gb`) and the cover URL, which the browser loads from Google and which is never copied or proxied. What it does not keep: Google's description. The Worker drops it before anything is cached or sent, so a Google hit has no blurb; picking it, "Fill details" and "Find covers and details" leave the blurb field empty. A blurb is filled only from Open Library (the existing lookup by work, for an Open Library hit) or typed by the user.
- Quota: Google does not publish the Books API limit; community reports say 1,000 requests a day per Google Cloud project, so read the real figure under APIs & Services > Quotas for `books.googleapis.com`. Nothing else shares the key here. One lookup costs at most one Google request and one Worker request; a cache hit costs no Google request. On `429` or a 5xx from Google the route falls back to Open Library, and when that has nothing it answers `busy` with the wait. The "Find covers and details" pass reads `retry`, backs off, and stops with "busy" when the wait is over a minute.
- Attribution, as Google's branding page asks: a Google result list shows the "Powered by Google" graphic (hosted by Google, shown unchanged), a "Google Books" link of at least 44 px on every result, and "Details from Google Books". An Open Library list says "Details from Open Library". Covers and the graphic load straight from Google in the browser, without a referrer, so Google sees which volumes are on screen; the Worker hides only the search.
- No analytics, and the route logs nothing, not even the query. Tests use recorded, hand-trimmed payloads in `test/fixtures/google` and `test/fixtures/openlibrary` and an injected `fetch`; nothing in them is a real key.

## Movies and series lookup

- `GET /api/lookup/screen` sits under `/api/*`, so Cloudflare Access protects it, and answers only a signed-in caller. Parameters: `kind` (`movie` or `series`) with `title` (2 to 200 characters) and an optional `year` (1880 to 2200), or `kind` with `id` (a positive integer, to refresh a row that has a TMDB id). The two forms never mix; anything else, a repeated or unknown parameter included, is `400 {"error":"bad_query"}`. The answer is `{"hits":[...]}`, at most 8 in TMDB's order: `kind`, `tmdb`, `title`, `original` (only when it differs from the title), `year`, `cover` (`null` or `https://image.tmdb.org/t/p/w342/<file>.jpg`). Failures are `{"error":"busy","retry":<seconds>}` with `Retry-After` (429 from TMDB keeps its wait, 1 to 3600; a TMDB 5xx is 503 with 30) or `{"error":"failed"}` (502, for a refused token, any other error status, a bad body, a timeout, or no token). An error body never holds the upstream URL or text. Like `/api/lookup` it is read-only, carries no per-partner data and is not in `SIDED`.
- It calls only `https://api.themoviedb.org/3/search/movie`, `/search/tv`, `/movie/{id}` or `/tv/{id}`, never `/search/multi`: the title goes in the `query` value, with `include_adult=false`, `page=1` and, when a year was typed, `primary_release_year` or `first_air_date_year`. `language=id-ID` is asked first and `en-US` only when that answers with no hit; an error in the first pass ends the lookup and is never taken for an empty answer. Every call has 3 seconds and a 256 KiB body cap (a compressed bomb is cut at the cap while it decompresses).
- The secret is `TMDB_TOKEN`, a TMDB API Read Access Token: `wrangler secret put TMDB_TOKEN`. It is optional: without it, or with a blank value, the route answers `failed` and makes no call. Locally, put it in `.dev.vars` (`.dev.vars.example` has the empty line). It is read only in `worker/screen.ts` and sent only as `Authorization: Bearer`, so it is in no URL, query string, response, log line, cache key or cache entry, and `npm run check` fails if the name or the API host reaches `dist/client`. The Worker sends the same `User-Agent` as for Open Library, `Nestora/1.0 (+https://nestora.atqamz.com)`, and follows no redirect.
- TMDB's terms (API Terms of Use, read 26 October 2026) allow non-commercial use with attribution and forbid caching its data for longer than 6 months. Nothing is kept long: the Workers Cache API holds an answer for at most 24 hours (`max-age=86400`) under `https://lookup.invalid/screen/v1?kind=...&title=...`, each entry with its own timestamp, and an older, future-stamped or unstamped entry is not served. A list or a definite empty answer is kept; an error, a 404 on the id form, or a lookup whose second pass failed is not. The Worker keeps six fields per hit and drops the rest (overview, genres, cast, ratings, popularity, backdrop) before anything is cached or sent; a poster path becomes a cover only in the plain `/<file>.jpg` shape, on the fixed `w342` URL. Images are never copied, proxied or resized.
- If TMDB ends the licence, remove the secret: the route fails cleanly and nothing else depends on it. Only the title, the kind and an optional year leave Nestora. The route logs nothing, not even the query. Tests use invented payloads in `test/fixtures/tmdb`, never recorded TMDB content, and an injected `fetch`.
- In the app: the Add a movie and Add a series sheets list up to eight matches from two letters, 400 ms after the last keystroke. Picking one fills the title, the original title, the year (only while the Year field is empty: a typed year stays), the poster URL (`data.cover`), the id (`data.tmdb`) and the day it was fetched (`data.tmdb_at`), and nothing else; "Add as typed" saves with none of those three keys. A match that is already on the list says "Already on your list" and can still be added. Changing the title drops the pick and clears a year the pick filled, never one that was typed. Enter saves what the button says, so while matches show it saves "Add as typed". Lookup unavailable, slow or empty never blocks typing.
- Posters and privacy: posters load straight from TMDB's image CDN, `https://image.tmdb.org/t/p/w342/...`, in the browser, lazily and without a referrer, so TMDB sees the phone's IP address and which posters are on screen; the Worker hides only the search. A movie's or series' `data.cover` accepts only that one URL shape (`https://image.tmdb.org/t/p/w342/<file>.jpg`); a book's `cover` also accepts Open Library and Google Books hosts, as before. They are never copied, proxied or resized, and a missing or failed poster draws the generated cover. A lookup sends only the typed title, the kind and an optional year to the Worker and from it to TMDB, never a partner's name, a note, a rating or who picked it.
- Attribution (API Terms of Use section 3, re-read 26 October 2026, last updated 20 October 2023): the notice "This application uses TMDB and the TMDB APIs but is not endorsed, certified, or otherwise approved by TMDB." and TMDB's approved short logo, `public/tmdb.svg`, served unmodified (2,065 bytes, SHA-256 pinned by `test/tmdb-credit.test.ts`, 12 px tall at the default text size, never given another width, a transform or a filter). They show under the match list, at the foot of the Movies and Series screens and detail pages whenever a row has a poster or an id, and in Settings under Credits.
- Expiry (API Terms of Use section 1.C: nothing from TMDB cached for more than 6 months): `data.tmdb_at` is the day a row's poster URL (`cover`) and id (`tmdb`) were fetched. Under 120 days old, nothing happens. From 120 to 169 days, or when the row has no id, the screen offers Find posters. At 170 days or more, or when a row has a poster or an id and no day, a sweep clears it: `Shell` runs `sweepExpired` beside the undo sweep whenever the rows change, the store is released from its paused state, the side is confirmed or the first answer from the server arrives, and sends one patch per row that sets `cover`, `tmdb` and `tmdb_at` to `null` and nothing else, so the title, year, original title, rating, status and note stay. Deleting a movie or a series clears the same three keys in the same write: the Worker always sends the three-key purge in the delete statement, whatever the row held when the request read it, so a poster write that lands in between cannot survive on the tombstone, and an update that read the row live cannot write a row that was deleted since (its statement requires `deleted_at IS NULL`), so an edit that loses that race is dropped without a rejection or a retry (the answer is 200 with the tombstone in `rows`, the phone drops its copy, and Undo restores from the live copy the phone still holds), and it does it when it soft-deletes the row and the phone's own copy does it at once, so a tombstone, the JSON export and the partner's phone hold none of them. Undo (the delete toast and the detail form) sends the three keys back with the revive, from the row the phone still holds, so a mis-tapped delete keeps its poster; that copy lives in the phone's memory only, so after a reload the Gone page's Undo brings the row back with no poster and no id (Find posters offers it again), and Undo from the partner's open detail page restores the keys of that phone's last live copy, with their old day; the Worker accepts a revive that carries only those keys on a movie or a series, and ignores a revive that carries anything else, or any change to a deleted row. `migrations/0003_purge_deleted_posters.sql` strips the keys from the tombstones that already exist and bumps `rev` once, so every phone pulls the cleaned rows (rows are stamped with `rev + 1` first, then `rev` moves, so it also holds when run statement by statement, and a run that finds nothing to purge changes nothing, `rev` included); the deploy job applies it with `wrangler d1 migrations apply wp --remote` before `wrangler deploy`, like every migration. The migration bumps `updated_at` on the rows it cleans, like any write, so an export shows the change; `rev` is what phones pull by. Known gap: the old Worker can write a tombstone that keeps the three keys between the moment 0003 is applied and the moment the new Worker is live (a few minutes inside one deploy job), and 0003 cannot purge it because it has already run. Those tombstones may keep their TMDB keys until the next migration purges them. That follow-up migration (the same statements as 0003, harmless to apply again: a run that finds nothing changes neither rows nor `rev`) is planned right after this PR merges, with no date promised. Until then the keys are harmless to the app (never shown, never exported by the app UI), but they sit in D1 and in the JSON export, so this stays a known, short, temporary gap against the TMDB cache clause. The sweep makes no write while the side is unconfirmed (the store refuses it) and runs again on the next change; two phones sweeping at once clear the same keys and leave one result. A stamp more than one day in the future counts as missing and is swept like one (a stamp one day ahead is fresh, for a time zone ahead of the one that wrote it). The sweep's "today" is the server's, never the phone's: the store keeps the offset between the `Date` header of an answer from `/api/sync` (only a 200 with the sync body shape) and its own clock, and `Shell` turns the server's time into a day in the app's time zone, so a phone with a wrong clock sweeps by the right day. A `Date` is not trusted blindly (`src/store/server-clock.ts`): one 400 days or more from the phone's clock is ignored; one more than a day earlier than the last one taken is ignored; one within a day of the phone's clock is taken at once; any other needs a second answer in a row that agrees with it within a day, and, when the rows hold a `tmdb_at` more than a day after it, is not taken at all. So a broken or replaying proxy cannot make the sweep clear a fresh poster with one odd `Date`, and a phone whose clock is off by days starts sweeping on its second answer. With no answer yet (offline since the start, or a reply with no `Date` header) the sweep waits and writes nothing; Find posters and the day stamped on a picked match use the same day when it is known and the phone's own otherwise (a match picked before the first answer, on a phone whose clock is more than a day ahead, carries a stamp the next sweep clears as a future one: the poster, nothing else). A sweep never happens on a phone whose clock is 400 days or more off, or whose clock is more than a day ahead and that holds a row it stamped itself before its first answer; the partner's phone, with the right clock, clears those rows. 170 days is about 5.6 months, which leaves 12 days under the six-month limit for a phone that stays closed: it sweeps the next time it opens.
- Dates: the first stored `tmdb_at` is 26 October 2026, the day the lookup merged. Its row reaches 120 days on 23 February 2027 (the first Find posters offer) and 170 days on 14 April 2027 (the first purge); six months from it is 26 April 2027. The sweep and Find posters must be deployed before 23 February 2027.
- Find posters: the Movies and Series screens show "N posters need a refresh" and a Find posters button when a row has no id or its day is 120 days old or more. It runs one row at a time, about one request a second (`GAP_MS`), backs off on a busy answer, stops after three in a row, and stops at once on Stop, on leaving the page or when the phone goes offline; a line above the button counts the rows done, and when a pass ends on its own the focus moves to that line, which keeps its height (the Stop button stays in the layout, hidden) so the list below does not jump. About one request a second holds between the phone and the Worker; a title with no answer in `id-ID` makes the Worker ask TMDB a second time in `en-US`, so TMDB can see about two a second, far under its limit. It fills only what is empty and never writes a title. Before each write the pass reads the row again from the store and writes only if its title, original title and year are still the ones the lookup was asked about; otherwise the row is skipped and counted as not sure. What remains is the sync lag: a rename the phone has not pulled yet cannot be seen, and the Worker applies the field-level patch without a condition. A hand-typed row TMDB never matched is counted again in every session (the pass remembers only within the session). The detail page of a row that holds a poster or an id has Remove poster, which clears `cover`, `tmdb` and `tmdb_at` with Undo, so a wrong match can be detached; it also clears a cover on another host, which the validation would otherwise keep the row from being edited with. A refresh by id keeps the old poster URL, with the new day, when TMDB answers without one. A row with an id is refreshed by id: the new day, a changed poster (never replaced by nothing), and an original title or year only if the row has none. An id TMDB no longer knows clears `cover`, `tmdb` and `tmdb_at` like the sweep. An answer about another id than the one asked is a failure, never a purge. A row without an id is searched by title and year, and written only when exactly one hit has a title or original title equal to the row's after folding case, accents and punctuation and, when the row has a year, the same year; no hit counts as no match, and two matches, or hits that are not the row, count as not sure and nothing is written. The routine is `findDetails` with the attempt passed in, the same loop as books' Find covers and details.

## Bootstrap

The top-level D1 binding in `wrangler.jsonc` holds the real production `database_id`. Only `env.dev` keeps the all-zero placeholder, which must never reach production. The bootstrap that created the database is in section 8 of `docs/infra.md` on the `docs` branch (`git show docs:docs/infra.md`).

## Names that still say wp

The product is called Nestora. These internal identifiers keep the old name because renaming them costs data or a migration for no user benefit:

| Identifier | Why it stays |
|---|---|
| Worker script `wp`, `dist/wp/` | the deploy target and the build path follow it |
| D1 database `wp`, KV binding and title | a new database means export, import and a new epoch |
| IndexedDB `wp-a`, `wp-b`, legacy `wp`, `localStorage` `wp-side` and `wp-theme`, `sessionStorage` `wp.timer.*` | a rename would orphan data already on the devices |
| `X-Wp-Side` header | both sides must agree during a deploy |
| Feed UID suffix `@wp.atqamz.com` | a new suffix re-creates every event in subscribed calendars |
| `wp-private/` in `.gitignore`, the live host `wp.atqamz.com` | still the live host and a local folder name |
